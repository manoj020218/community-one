# CODEX IMPLEMENTATION PROMPT

## SAMA Module — Staff, Attendance, Management and Access

You are working inside an existing professional multi-society Society Management Platform.

Your task is to design, implement, test and document a new independently deployable plugin module named:

# SAMA — Staff, Attendance, Management and Access Module

The module must be implemented in a separate folder and integrated with the existing platform while disturbing the existing codebase as little as possible.

Suggested module folder:

```text
SAMA/
```

The module must follow the existing platform’s:

* Authentication
* Society-level tenant isolation
* Role and permission system
* Module enable/disable mechanism
* Device mapping
* Audit logging
* Notification framework
* File storage
* UI theme
* Routing conventions
* API conventions
* Test framework

Do not rewrite existing working systems unnecessarily.

The SAMA module must be suitable for a professional product with an expected operational life of at least ten years.

* Identity records

* Attendance

* Work allocation
* Flat association
* Payroll where applicable
* Household payment records where applicable
* Service-request assignment
* Compliance-document tracking

* Reports and audit trails

# 2. Mandatory coding rules

## 2.1 File-size restriction

No source-code file may exceed 200 lines.

This applies to:

* Backend files
* Frontend files
* Models
* Services
* Controllers
* Routes
* Validators
* Components
* Hooks
* Utilities
* Tests
* Device adapters
* Payroll logic
* Attendance logic

When a file approaches 180 lines, split it by responsibility.

Do not compress code artificially to satisfy the rule.

## 2.2 Minimal disturbance to core platform

Before implementation:

1. Inspect the current repository.
2. Identify the plugin/module pattern.
3. Identify the existing module registry.
4. Identify the permission system.
5. Identify the society tenancy mechanism.
6. Identify device mapping.
7. Identify resident and flat models.
8. Identify visitor-management integration points.
9. Identify notification infrastructure.
10. Identify current audit logging.
11. Identify whether payroll, attendance or access-control abstractions already exist.

Keep SAMA-specific business logic inside the SAMA folder.

Core changes should be limited to:

* Module registration
* Route registration
* Permission registration
* Navigation registration
* Shared-device event registration
* Shared notification registration
* Shared audit registration
* Dependency injection registration
* Society settings registration

Do not move unrelated existing code into SAMA.

## 2.3 Icon integrity

Use the platform’s existing icon library.

Do not:

* Replace icons with ASCII characters
* Replace icons with Unicode symbols
* Replace icons with emojis
* Replace icons with text like `+`, `x`, `<`, `>`, arrows or symbols
* Modify icons in unrelated modules
* Convert icons into HTML entities

Add a final review and test to ensure no icon has been replaced by ASCII text.

## 2.4 Technical quality

Use:

* TypeScript strict mode
* Explicit DTOs
* Runtime validation
* Tenant-aware repositories
* Structured logging
* Central error handling
* UTC timestamp storage
* Society timezone display
* Database indexes
* Idempotent attendance ingestion
* Idempotent payroll processing
* Immutable payroll-posting records
* Audit logs
* Access-event deduplication
* Secure file handling
* Configurable policies rather than hardcoded society assumptions

Use `en-IN` formatting for currency and dates where appropriate.

Store money in paise:

```ts
amountPaise: number
```

Do not use floating-point money calculations.

# 3. EdgeFolio code reuse

A similar attendance, access-control and payroll implementation may already exist in the EdgeFolio project.

Before implementing attendance, access or payroll from scratch:

1. Ask whether the EdgeFolio codebase is available in the current repository, workspace, connected GitHub source or a local reference folder.
2. Search for reusable:

   * Attendance event ingestion
   * Access-device mapping
   * Shift rules
   * Payroll calculations
   * Salary structures
   * Leave management
   * Overtime logic
   * Payslip generation
   * Device synchronization
   * Employee identity mapping
3. Reuse proven code only where:

   * Licensing permits
   * Architecture is compatible
   * Security is acceptable
   * Tenant isolation can be guaranteed
   * Code quality meets current standards
4. Refactor reused code into clean SAMA-specific adapters.
5. Do not blindly copy old code.
6. Add regression tests around all reused logic.
7. Document each reused component in:

```text
SAMA/EDGEFOLIO_REUSE.md
```

The EdgeFolio implementation may save development time, especially for:

* Attendance
* Access-control machines
* Employee-device mapping
* Shift handling
* Payroll
* Payslip generation

However, the Society Management Platform’s current architecture remains the source of truth.

# 4. Module enablement

SAMA must work as an optional society plugin.

Required behavior:

* Platform super admin can enable or disable SAMA society-wise.
* The module appears only when enabled for that society.
* Backend API access must be blocked if disabled.
* Direct URL access must not bypass module entitlement.
* Background jobs must skip societies where SAMA is disabled.
* Historical data must not be deleted when disabled.
* Re-enabling must restore access.
* Device events may still be safely retained according to platform policy even when temporarily disabled.
* Shared member-access features must not automatically expose staff-management data.

Create a module manifest containing:

```text
moduleCode: SAMA
displayName: Staff Management
version
requiredCoreVersion
permissions
routes
navigation
settingsSchema
backgroundJobs
domainEvents
deviceCapabilities
optionalDependencies
```

# 5. Domain separation

The module must not treat all people as one generic employee type.

Create clear domain concepts for:

```text
SOCIETY_EMPLOYEE
HOUSEHOLD_STAFF
SERVICE_POOL_WORKER
CONTRACTOR_EMPLOYEE
TEMPORARY_WORKER
```

A person may have more than one role over time, but active engagements must remain explicit.

Example:

* A plumber may be on society payroll.
* Another plumber may be a service-pool worker.
* A third plumber may be attached regularly to certain flats.

Do not determine payroll behavior only from occupation name.

Use engagement type and employer type.

# 10. Attendance processing

Attendance ingestion must be idempotent.

Use a unique key based on:

```text
societyId + deviceId + deviceEventId
```

Where device event ID is unavailable, derive a careful deduplication signature from:

```text
deviceId + credential + eventTime + eventType
```

Do not discard legitimate repeated events only because they are close in time.

Support:

* Entry and exit
* Check-in and check-out
* Multiple shifts
* Night shifts crossing midnight
* Missing punch
* Manual correction
* Late arrival
* Early exit
* Half day
* Overtime
* Weekly off

* Grace period

* Attendance approval

Examples:

### Security guard

* Allowed according to shift

* Temporary access
* Linked to work order
* Allowed only during service window
* Restricted to security office or approved zones

### Tank-cleaning team

* Work-order access
* Multiple team members
* Valid on scheduled date
* Access to tank or service area only

Every denied access event should record a safe reason code.
