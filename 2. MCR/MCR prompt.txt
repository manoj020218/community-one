# CODEX IMPLEMENTATION PROMPT

## MCR Module — Maintenance Collection and Receipt Management

You are working inside an existing professional Society Management Platform built as a multi-society, multi-tenant, modular application.

Your task is to design, implement, test and document a new independently deployable plugin module named:

# MCR — Maintenance Collection and Receipt Module

The MCR module must be implemented in a separate folder and integrated into the existing platform with the minimum possible disturbance to the existing codebase.

The module must follow the existing platform architecture, design system, authentication, authorization, audit logging, notifications, file storage, tenant isolation and coding conventions.

Do not rewrite working platform functionality merely to accommodate the new module.

---

# 1. Product vision

The MCR module will allow a society to:

* Define maintenance charges.
* Generate maintenance demands.
* Send collection requests.
* Send reminders.
* Record manually received payments.
* Verify payments.
* Generate receipts.
* Download and share receipts.
* Maintain flat-wise and society-wise ledgers.
* Track dues, advances, credits, waivers and penalties.
* Prepare collection reports.
* Support optional payment-gateway integration in the future.

For the initial release, all payment confirmation will be manual.

The rest of the process should be automated as much as possible.

The software is intended for societies commonly operated by unpaid committee members. Therefore:

* Data entry must be minimal.
* Repetitive work must be automated.
* Bulk actions must be available.
* Default values should be prefilled.
* Common actions should take the fewest possible steps.
* Every financial action must remain traceable.
* Mistakes must be reversible through controlled adjustment workflows rather than destructive editing.

The module must be suitable for a professional product with an expected operating life of at least ten years.

# 2. Mandatory development rules

Follow these rules throughout implementation.

## 2.1 File-size rule

No source-code file should exceed 200 lines.

This applies to:

* Backend files
* Frontend files
* React components
* Services
* Controllers
* Repositories
* Validation schemas
* Utilities
* Tests
* Configuration files containing executable logic

When a file approaches 180 lines, split it by responsibility before continuing.

Do not artificially compress code onto fewer lines to satisfy this rule.

Code must remain readable and easy to debug.

## 2.2 Existing-code safety

Before making changes:

1. Inspect the repository structure.
2. Identify existing patterns for modules, permissions, routing, models, services, controllers, UI pages, notifications, files, audit logs and tests.
3. Identify existing society-level module enable/disable logic.
4. Identify the existing authentication token and tenant context.
5. Identify existing reusable UI components.
6. Identify the existing icon library.
7. Identify existing payment or receipt-related abstractions.
8. Identify whether the repository already has queues, schedulers, workers, email, SMS or WhatsApp adapters.

Do not create parallel infrastructure when suitable shared infrastructure already exists.

Do not rename existing APIs, models, routes, roles or permissions unless absolutely required.

Do not modify unrelated modules.

Every existing regression test must continue to pass.

## 2.3 Icon safety rule

Codex has previously replaced icons with ASCII characters or textual symbols. This must not happen.

Strictly follow these rules:

* Use the icon library already used by the platform.
* Preserve existing icon components and imports.
* Do not replace icons with ASCII characters.
* Do not replace icons with Unicode symbols or emojis.
* Do not use characters such as `>`, `<`, `+`, `x`, `*`, arrows or text labels as visual substitutes for proper icons.
* Do not alter existing icons in unrelated screens.
* Do not convert icon components into HTML entities.
* Do not add arbitrary emoji icons.
* Verify the final UI visually and through code review for accidental ASCII icon replacement.

## 2.4 Quality rules

Use:

* TypeScript strict mode.
* Explicit interfaces and DTOs.
* Runtime validation for external inputs.
* Centralized error handling.
* Structured logging.
* Database indexes.
* Idempotent financial operations.
* Tenant-aware repository methods.
* UTC storage for timestamps.
* Society timezone for display and scheduled actions.
* Indian currency formatting through `en-IN`.
* Decimal-safe money handling.

Never use JavaScript floating-point arithmetic directly for money.

Store monetary values in the smallest currency unit, such as paise:

```ts
amountPaise: number
```

For example:

* ?1,250.50 must be stored as `125050`.
* UI and reports should format it as `?1,250.50`.

Never store financial amounts as free-form strings.

The module must only be visible and usable when the main platform enables MCR for a society.

Required behavior:

* Platform super admin can enable or disable MCR society-wise.
* Society users cannot bypass this restriction by directly calling an API.
* Every MCR backend endpoint must check:

  * Authenticated user
  * Active society context
  * Society module entitlement
  * Required permission
* MCR routes must not appear in the UI when the module is disabled.

* Disabling the module must not delete historical data.
* Re-enabling the module must restore access to historical records.
* Background jobs must skip societies where MCR is disabled.
* Public receipt verification, when enabled, should continue to work according to retention policy even if the module is later disabled.

Create a clear module manifest with:

* Module code: `MCR`
* Display name: `Maintenance & Receipts`
* Version
* Required core version
* Permissions
* Routes
* Navigation entries
* Settings schema
* Background jobs

# 5. Multi-tenant data isolation

This is a multi-society platform.

Every MCR record must include `societyId`.

Where applicable, include:

* `flatId`
* `residentId`
* `towerId`
* `createdBy`
* `updatedBy`
* `verifiedBy`

No query may rely only on a document ID.

Every read and write must validate the active society.

For example, never do:

```ts
findById(id)
```

Instead use a tenant-aware operation such as:

```ts
findOne({
  _id: id,
  societyId: activeSocietyId
})
```

Create and test compound indexes containing `societyId`.

Add tests proving that users of Society A cannot read or modify Society B’s MCR data.
